# 用户级元规则(UR-xx)

> 提炼自 `HAnchor\**\.hanchor\memory\*.md` 约 30 份会话记忆(2026-09 ~ 2026-11)。
> 定位:现有规范体系(1528 份 skill 规范)缺少**用户级 scope 层**——这些规则高于任何单个 skill,
> 来自真实工作教训,编号规则与 html-review 的 `SC-xx` 体系同构,可按编号引用与回归。

## 判断与方法论

### UR-01 "不支持"的结论门槛必须高于"支持"

判断一个模型/系统的能力边界前,必须**穷举参数空间**(字段位置 × 字段名 × 取值格式),不能只测默认调用方式就下结论。漏测导致误判。
来源:2026-09-17 MiMo voiceclone 实验——`audio.voice` 花了三层才试对:位置(顶层非 message 内)→ 字段名(`voice` 非 `data`)→ 格式(DataURL 非裸 base64)。

### UR-02 API 结论以实测为准,不以文档为准

文档口径与实测口径必须分开记录;未实测的内容显式标注"未知,不要当成结论"。
来源:`MIMO_API.md`(全篇实测探测,含"以下未实测,标注为未知"一节)。

### UR-03 性能判断以计数器为准,不按经验百分比

下容量/性能结论前先读命中率和实际物理读;经验值("内存百分比")会被实测推翻。
来源:2026-09-15——第一轮"512M 太小"的判断被推翻:物理读总共 ~120MB,512M 够用。

### UR-04 不要为消除报错而调低资源 request

校验报错(request ≥ limit)应调高 limit,而不是压低 request。对数据库是反向优化,加剧 CFS 限流。
来源:2026-09-15 容器资源表单案例。

## 知识管理

### UR-05 跨窗口可复用的知识必须落成 skill,不落目录级文档

目录内文档换个工作目录就失效;要沉淀就进 skill 体系。
来源:2026-09-17 会话教训。

### UR-06 待办清单追加式维护,不重排历史

ID + 优先级 + 状态 + 提出日期;新增条目追加到末尾;每条必带"待确认"与"风险"段。
来源:Claw 工作区待办协议约定(2026-10-19)。

## 平台/环境事实

### UR-07 Windows:写入注册表环境变量后,已运行进程读不到

进程环境块是启动时快照(`HKCU\Environment` 同理),改完必须重启应用才生效。
来源:2026-09-17。

### UR-08 ES map 类型字段数有硬上限,动态增长的标签必须用 nested

map key 方案字段数 ≈ 2 × 标签种类数,`index.mapping.total_fields.limit` 默认 1000,标签种类超约 400 就写入报错。标签固定且少可用 map,动态增长必须改 nested。
来源:2026-09-17 `lv_tags` 案例。
