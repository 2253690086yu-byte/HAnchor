# 技术设计文档(design-doc)

> 读者:评审者与实现者,拿着它拍板并开工。
> 定位:把"要怎么做"讲到别人能挑出毛病为止。

## 章节结构与篇幅配比

| # | 章节 | 配比 | 写什么 | 不写什么 |
|---|---|---|---|---|
| 1 | 背景与问题 | ~10% | 现状、触发本次设计的具体问题,引用 issue/数据 | 战略铺垫、历史长文 |
| 2 | 目标 / 非目标 | ~5% | 可验证的目标;明确排除项 | "提升用户体验"式泛目标 |
| 3 | 方案总览 | ~15% | 一张架构/数据流图 + 三五句讲解 | 逐模块细节 |
| 4 | 详细设计 | ~40% | 接口、数据结构、关键路径、边界条件 | 粘贴大段代码 |
| 5 | 备选与取舍 | ~15% | 至少一个真实备选,否决理由对着目标讲 | "综合考虑后选择" |
| 6 | 影响面与风险 | ~10% | 波及模块、兼容性、失败模式与预案 | 只列好处 |
| 7 | 里程碑(可选) | ~5% | 分阶段交付与每阶段验证点 | 精确到天的排期 |

**必留节:2、5、6**——没有非目标和取舍的设计无法评审。

## 最小骨架

```markdown
# <方案名> 技术设计

## 1. 背景与问题
<现状 + 具体问题,附 issue/数据链接>

## 2. 目标 / 非目标
- 目标:<可验证>
- 非目标:<明确排除>

## 3. 方案总览
<架构图或数据流图 + 3-5 句讲解>

## 4. 详细设计
### 4.1 <接口 / 数据结构>
### 4.2 <关键路径>
### 4.3 <边界条件>

## 5. 备选与取舍
| 方案 | 优点 | 否决原因 |
|---|---|---|
| <备选> | | <对着第 2 节目标> |

## 6. 影响面与风险
- 波及:<模块清单>
- 风险:<失败模式 → 预案>

## 7. 里程碑
| 阶段 | 交付 | 验证点 |
|---|---|---|
```

## 反模式

- 备选节列一个稻草人方案一句话否决 → 取舍必须对着目标与约束
- 详细设计贴 200 行代码 → 讲结构与不变量,代码给链接
- 风险节写"暂无" → 至少交代兼容性与回滚方式
- 图和正文各讲一套 → 图里的每个框正文都要接住
