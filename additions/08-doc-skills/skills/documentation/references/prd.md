# 产品需求文档(PRD)

> 读者:设计与开发,拿着它排期并验收。
> 定位:把"要做什么、做到什么程度算完"定义到不需要口头补充。

## 章节结构与篇幅配比

| # | 章节 | 配比 | 写什么 | 不写什么 |
|---|---|---|---|---|
| 1 | 问题与机会 | ~10% | 用户当前怎么绕过这个问题,代价是什么 | 市场分析 |
| 2 | 目标与成功指标 | ~10% | 业务目标 + 可度量指标(基线 → 目标值) | 不可度量的口号 |
| 3 | 用户故事与场景 | ~15% | 谁、在什么场景、要完成什么、为什么 | 人物画像堆砌 |
| 4 | 功能需求 | ~35% | 按模块列需求,含异常流与边界 | 交互细节与实现方式 |
| 5 | 非目标 | ~5% | 本期明确不做的事 | — |
| 6 | 验收标准 | ~15% | Given/When/Then 或清单,可逐条打勾 | 复述需求 |
| 7 | 依赖与风险 | ~10% | 上下游依赖、合规、时间风险 | 团队排期细节 |

**必留节:2、5、6**——没有指标、非目标和验收标准的 PRD 无法验收。

## 最小骨架

```markdown
# PRD:<功能名>

## 1. 问题与机会
<现状绕行方式 + 代价>

## 2. 目标与成功指标
| 指标 | 基线 | 目标 |
|---|---|---|

## 3. 用户故事与场景
作为<谁>,在<场景>下,我想<完成什么>,以便<价值>。

## 4. 功能需求
### 4.1 <模块>
- 需求:<正常流>
- 异常流:<边界 / 失败态>

## 5. 非目标
- <明确不做的事>

## 6. 验收标准
- [ ] Given <前置> When <动作> Then <结果>

## 7. 依赖与风险
- 依赖:<上下游>
- 风险:<合规 / 时间>
```

## 反模式

- 需求只写正常流 → 每条需求补异常流才算定义完整
- 验收标准复述需求 → 必须可独立执行、可打勾
- 技术方案写进 PRD → 移到 design-doc,两份文档分开
- 指标没有基线 → 没有基线的目标值无法判断达成
