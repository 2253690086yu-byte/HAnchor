# 决策记录(decision-doc / ADR)

> 读者:半年后想知道"当时为什么这么定"的人,包括未来的自己。
> 定位:存一个决定及其来路;不追求全面,追求可追溯。

## 章节结构

| # | 章节 | 写什么 | 不写什么 |
|---|---|---|---|
| 1 | 状态与日期 | 提出 / 已接受 / 已废弃 / 被 ADR-N 取代 | — |
| 2 | 背景 | 促成决策的约束与事件,两三段 | 完整系统介绍 |
| 3 | 决策 | 一句话、主动语态,说清做了什么决定 | 模糊的"倾向于" |
| 4 | 理由 | 证据、数据、约束如何推出该决定,可逐条核查 | 利益罗列、感受描述 |
| 5 | 备选与否决原因 | 每个备选一小段,否决理由具体到失败模式 | 树立靶子 |
| 6 | 后果 | 正面 / 负面 / 中性分开写,含引入的技术债 | 只写好处 |

**必留节:3、5、6**——没有备选与后果的不是决策记录,是通知。

## 最小骨架

```markdown
# ADR-<序号>:<决定标题>

- 状态:已接受(<日期>)
- 关联:<issue / design-doc 链接>

## 背景
<约束与触发事件>

## 决策
<一句话,主动语态>

## 理由
1. <证据 / 约束> → <推论>

## 备选与否决原因
### 备选 A:<名称>
<为何不选,具体到失败模式>

## 后果
- 正面:<>
- 负面:<技术债 / 维护成本>
- 中性:<依赖或边界变化>
```

## 反模式

- 一份 ADR 塞多个决定 → 一个决定一份
- 决策写成"经过讨论,大家认为" → 理由必须落到可核查的证据
- 备选只剩名字 → 每个备选给一段真实否决理由
- 过时 ADR 直接删除 → 改状态为"被 ADR-N 取代",保留否决链供后续翻案对照
