# 提案(RFC)

> 读者:受影响的各方,读完要能表态:同意 / 反对 / 有条件同意。
> 定位:把一个变更提议连同影响面摊开,推动共识。

## 章节结构与篇幅配比

| # | 章节 | 配比 | 写什么 | 不写什么 |
|---|---|---|---|---|
| 1 | 现状与痛点 | ~15% | 具体痛点、量化代价、谁在受影响 | 历史回顾长文 |
| 2 | 提议 | ~25% | 先一句话版本,再展开机制 | 实现级细节 |
| 3 | 影响面 | ~20% | 谁和哪些系统受影响,破坏性变更逐条列 | "影响不大" |
| 4 | 迁移路径 | ~15% | 分阶段计划,每阶段有可停点 | 一步到位 |
| 5 | 备选方案 | ~10% | 否决理由对着痛点讲 | 敷衍备选 |
| 6 | 回滚方案 | ~5% | 什么条件下退、怎么退回现状 | — |
| 7 | 开放问题 | ~10% | 未决项,标注需要谁拍板 | 假装全想清楚了 |

**必留节:3、4、6、7**——没有影响面和回滚的提案无法评审。

## 最小骨架

```markdown
# RFC:<提案名>

- 作者 / 日期
- 状态:征求意见(截止 <日期>)

## 1. 现状与痛点
<量化代价 + 受影响方>

## 2. 提议
一句话:<>
展开:<机制 / 流程 / 接口>

## 3. 影响面
| 对象 | 影响 | 是否破坏性 |
|---|---|---|

## 4. 迁移路径
| 阶段 | 动作 | 可停点 |
|---|---|---|

## 5. 备选方案
### <备选>:<否决原因,对着第 1 节痛点>

## 6. 回滚方案
<触发条件 + 退回动作>

## 7. 开放问题
- [ ] <问题>(需 <谁> 拍板)
```

## 反模式

- 状态栏不写征求意见截止日期 → 拖成僵尸帖
- 影响面只写受益方 → 破坏性变更必须逐条列并给迁移方式
- 开放问题藏进正文 → 显式列出并指定决策人
- 提议直接写成实现设计 → 机制讲到能判断可行性即可,细节留给 design-doc
